## 1. 问题现象

运行工作流后，运行中（`running` / `interacting`）的 step agent 卡片下，内嵌子代理对话区不再显示「最新 10 条消息流」，而是固定渲染降级占位：

```
[Deep diving...]
子代理正在独立会话中运行，实时消息请打开会话查看
[ 查看会话 ]
```

这与改版前（提交 `846ac17` 之前）的行为不一致——此前该位置会内嵌展示子代理会话的实时对话流（用户消息行 / assistant markdown / 工具卡 / turn-tail，最新 10 条节点，运行中流式）。

---

## 2. 根因分析：自洽死锁（self-fulfilling deadlock）

### 2.1 回归来源

提交 `846ac17` 在 `packages/client/StepChatPanel.tsx` 的 `StepChatPanel` 根组件中新增了一段**一次性版本探测**：

```tsx
// StepChatPanel.tsx（当前 main，约 207-218 行）
const [inlineChatSupported, setInlineChatSupported] = useState(false)
useEffect(() => {
  const snapshot = binding?.session.getSnapshot() as { nodes?: unknown } | undefined
  setInlineChatSupported(Array.isArray(snapshot?.nodes))   // ← deps 只有 [binding]，只采一次
}, [binding])

useEffect(() => {
  if (binding === undefined || !inlineChatSupported) return  // ← 被探测结果门控
  openSessionWindow(binding)
}, [binding, inlineChatSupported])
```

并据此把 `<StepChatBody>` 切到「`supported={inlineChatSupported}` + `!supported` 占位分支」：

```tsx
// StepChatBody（约 458-477 行）
if (!supported) {
  const runningNow = snapshot.running === true
  return (
    <div className={css.stepChatPanel} data-step-chat>
      <div className={css.stepChatEmpty}>
        {runningNow && <div className={chatCss.turnStatus}>Deep diving...</div>}
        <div className={css.stepChatHint}>
          {runningNow ? t('run.step.chat.runningUnavailable') : t('run.step.chat.unavailable')}
        </div>
        <div className={css.stepChatEmptyActions}>
          <Button variant="outline" onClick={onOpenSession}>{t('run.step.chat.openSession')}</Button>
        </div>
      </div>
    </div>
  )
}
```

> `846ac17` 之前的实现：`binding` 可用即**无条件**调用 `openSessionWindow(binding)`，直接渲染 `<StepChatBody session={...} t={t} />`（无 `supported` 门控）。

### 2.2 死锁链条

探测判据 `Array.isArray(snapshot?.nodes)` 在 **binding 刚解析、会话仍 cold（未 open）** 的瞬间采样，且 `useEffect` deps 只有 `[binding]`，**只采一次**：

1. `binding` 由 `undefined` → 可用时 effect 触发，此刻 `binding.session.getSnapshot()` 返回 **cold 快照**——子代理会话尚未 `open()`，conversation view 尚未拉历史 / 消费 mux 帧，`nodes` 尚未组装为数组 → `Array.isArray(undefined)` = `false`。
2. `inlineChatSupported` 被置为 `false`。
3. 因 `!inlineChatSupported`，第二个 effect **不调用** `openSessionWindow(binding)` → 会话永不 `open()` → `nodes` 永不填充。
4. deps 不含快照，即便后续 host 推送事件也不重判 → **永久停在占位**。

这与用户观测完全吻合：占位文案 `run.step.chat.runningUnavailable` 仅当 `snapshot.running === true` 才显示，说明 **binding 已解析、子代理确在运行**，但 `nodes` 仍非数组 → 探测 false → 占位。即「子代理在跑、消息在产生，面板却因死锁显示不出来」。

> 注：`846ac17` 注释声称「rc.2 cold 快照恒有 `[]`」——**该断言被用户真机症状证伪**：实际 cold 子代理快照的 `nodes` 并非数组（否则探测为 true、不会卡占位）。作者基于错误假设写了一道致命门控。

### 2.3 类型契约侧的反证

`@deepseek-ai/dsh-client-runtime@0.1.1-rc.2`（即当前部署版本，见 §0）的 `ConversationSnapshot`（`lib/types/client/sessions/conversation.d.ts`）明确：

```ts
export interface ConversationSnapshot {
  // ...
  /** Legacy top-level compatibility field mirrored from the registered Chat Definitions. */
  nodes: readonly ConversationNode[];
  partial: PartialAssistant | null;
  runningCalls: readonly RunningToolCall[];
  turnTimings: ReadonlyMap<number, { readonly startTime: number; readonly endTime?: number }>;
  // ...
  chat: ChatSnapshot;            // chat.legacy: LegacyConversationSlice（同源镜像）
  openState: 'cold' | 'loading' | 'open' | 'error';
}
```

`nodes` 是**顶级合法字段**（legacy 兼容镜像）。`buildStepChatFlow(snapshot)` 直接消费 `snapshot.nodes / partial / runningCalls / turnTimings`。即：**只要会话 `open()` 成功，`nodes` 就会被组装填充**。真正缺的只是「触发 open」这一步，而探测恰恰把它门控死了。

### 2.4 现有「正确的反应式判据」已存在，被一次性探测短路

`StepChatBody` 本身已有**每次快照变化都重判**的反应式检查（约 358-362 行），这才是 cold→open 过渡的正确姿势：

```tsx
const hasChatViewData = Array.isArray((snapshot as { nodes?: unknown }).nodes)
const rows = useMemo(
  () => (hasChatViewData ? buildStepChatFlow(snapshot as unknown as StepChatFlowInput) : []),
  [snapshot, hasChatViewData],   // ← 订阅快照，open 后 nodes 变数组即重渲染
)
```

外加 `openState` 三态处理（cold/loading → 加载占位；error → Round 25 退避重试 `open()`，1s→3s→10s 封顶）作为瞬时失败的安全网。即：**移除一次性探测后，cold→loading→open 的自然过渡 + 反应式 `hasChatViewData` + Round 25 重试，已完整覆盖所有边界**。

### 2.5 关于注释里「rc.1 open 会被 session/agent-busy 拒绝」的判断

`846ac17` 注释给出的探测理由是「rc.1 宿主对子代理普通 `open()` 会以 `session/agent-busy` 拒绝」。**该 agent-busy 拒绝确实存在**（用户后续真机确认：运行中点 step 进子代理 → "session/agent-busy" → 等一会才正常渲染）**，但探测不是正确的应对**：

- agent-busy 是**瞬态**：DSH 对**运行中**（turn 未 settle、parent address 未 durable）的子代理会话拒绝 `session.open()`；turn settle 后即放行。用户「改版前能正常显示」是因为改版前**无条件 open + Round 25 退避**——瞬时被拒时退避重试至 settle 后自然渲染。
- `846ac17` 的探测（cold 快照 `nodes` 一次性判）把「瞬态可自愈的 agent-busy」错误升级为「永不 open」→ 死锁（§2.2）。正确应对是 §3.4：移除探测 + 无条件 open + agent-busy 时显示 loading（非 error）+ settle（`running→false`）后自动重 open（Edit 6/7）——而非一次性放弃。
- `openSubagent(address)`（注释提到的「打开会话」）与 `session.open()` 是**两件事**：前者切换宿主会话视图到该子代理，后者把对话流拉进内嵌面板。前者不在自动 open 路径上。

结论：agent-busy 真实但瞬态；探测是错误应对（死锁）；正确做法是 §3.4 的 loading + settle 重 open。

### 3.4 运行中子代理 `session/agent-busy` 处理（Bug #1 修复的**必要配套**）

> 用户报：启动工作流后点**正在执行**的 step 进子代理 →「历史加载失败：subagent Sessions require their durable parent address（session/agent-busy）」，无真实消息；等一会再点才正常渲染。

**根因**：这正是 `846ac17` 当初加 `inlineChatSupported` 探测想绕开的 `session/agent-busy`——StepChatPanel 注释原话「普通 open 会被 host 以 `session/agent-busy`（subagent Sessions require their durable parent address）拒绝」。DSH 对**运行中**（turn 未 settle、parent address 未 durable）的子代理会话拒绝 `session.open()`。§3.1 Edit 1 移除探测、恢复无条件 `open()` 后，**运行中 step 会重现 agent-busy 错误**——探测用死锁换来了「不闪错」，移除探测后须显式处理 agent-busy，否则 Bug #1 修复不完整（只是把死锁换成 error 闪烁）。

**现状（仅靠 Round 25 退避不够）**：`step-chat-retry.ts:18` `STEP_CHAT_RETRY_DELAYS_MS = [1000, 3000, 10000]`——3 次重试、14s 封顶。长 turn 子代理 settle >14s 即放弃，停在 error 占位；用户须**重新点击**（重挂载→新一轮重试）才渲染——即用户观测的「等一会再点才正常」。

#### Edit 7｜`StepChatBody` 加 settle 后重 open 的 effect（覆盖长 turn，超越 Round 25 的 3 次）

`packages/client/StepChatPanel.tsx`（与现有 Round 25 retry effect 并列，约 L364-385 之后）：

```tsx
// 运行中子代理 session/agent-busy：等 turn settle（snapshot.running→false）后重 open()。
// Round 25 的 3 次退避（1s→3s→10s）对长 turn 子代理可能不够；running→false 是
// open 可用的权威信号——settle 后重 open，无需用户手动重点击。
useEffect(() => {
  if (snapshot.openState !== 'error') return
  if (snapshot.openError?.code !== 'session/agent-busy') return
  if (snapshot.running) return  // 仍 running，等 settle
  const opener = session as unknown as { open(): Promise<void> }
  void opener.open().catch(() => {
    // settle 后 open 仍失败：保持 error 占位（Round 25 继续退避）。
  })
}, [snapshot.openState, snapshot.openError, snapshot.running, session])
```

> 行为：运行中点击 step → open() → agent-busy → `openState='error'` → Edit 6 显示 **loading**（不闪 error）→ Round 25 退避重试 + Edit 7 在 `running→false` 时重 open() → settle 后 open 成功 → `openState='open'` → 渲染消息流。**全程无需用户重点击**。

## B2. 静态分析结论（已排除的范围 + 仍存的定位缺口）

### B2.1 `snapshotEvents()` 返回形状是合法的

dsh-session `lib/index.js:1342-1346`：

```js

        this.eventsSnapshot ??= Object.freeze([...this.log]);   // ← 冻结的 this.log 拷贝
        return this.eventsSnapshot;
    }
    return Object.freeze(this.log.slice(fromSeq, toSeqExclusive));

```

无参调用返回 `this.log`（会话事件日志）的冻结拷贝——是合法 `SessionEvent[]`（含 `type`/`seq`/`time`/`data`），**无 undefined 元素**。所以「事件形状不对」不是病因。

# Bug #3：子代理会话 Token 追踪「session corrupt: message must have tool source at seq N」（已定位：**非 sandore，DSH 侧**）

> 用户报：点 step 进子代理会话 → 轨迹右侧 Token 追踪报：
> `加载失败：SessionQueryError: stored session "c6b17916-…" is corrupt: stored session "…" failed validation: Error: session event at seq 365 message must have tool source`

## C1. 现象

点 step 进子代理会话 → Token 追踪读取持久化会话时，DSH `session-query` 校验失败：某 `tool/result` 事件（seq 365）的 `message.source.callId` 为空字符串 → 触发 rc.1 校验「message must have tool source」（dsh-session `assertMessageEventShape` L1185：`sourceRecord["callId"] === ""` 即抛）。整个会话被判定 corrupt → Token 追踪「加载失败」。

## C2. ✅ 已定位（dump corrupt 会话事件）：**非 sandore，DSH agent loop 写空 callId**

经动态 Cordis 插件调 `sessionPersistence.inspect`（也抛同错，证校验在底层读取即触发）+ 直接解压会话文件 `session.jsonl.zstd`（112 个 zstd 帧，逐帧解压拼出 190 条事件）dump 出 seq 365 等事件，**真凶不是 sandore**：

```
seq 365 tool/result  source={kind:"tool", callId:""}   ← callId 空串
        content[0]={type:"tool-result", toolCallId:"", content:[{text:"Error: question 'ca74605a-…' rejected"}], isError:true}
```

**关键**：**所有 `tool/call` 事件的 `data.callId` 都是空串**——无论工具是 sandore 的还是 DSH 内置的：

```
seq 364 tool/call sandore_ask_user_question  data.callId=""
seq 366 tool/call glob                        data.callId=""   ← DSH 内置工具也空
seq 480 tool/call read                        data.callId=""   ← DSH 内置
seq 742 tool/call edit                        data.callId=""   ← DSH 内置
seq 910 tool/call send_message                data.callId=""   ← DSH 内置
```

对应的 `tool/result` 的 `source.callId` 也 `""`（5 条 corrupt：seq 365/367/481/743/911）。

**结论**：DSH 的 agent loop / 工具执行链**没给 `tool/call` 生成 `callId`**（写空串），所有工具（含 DSH 内置 `glob`/`read`/`edit`/`send_message`）全中招；空 callId 透传到 `tool/result.source.callId` → rc.1 校验「message must have tool source」失败。这些 `tool/call`/`tool/result` 事件是 **DSH agent loop 写的**（子代理跑工具时 DSH 记录），**不是 sandore 写的**——sandore 只写 `user/message` 投递消息（`deliverChildPrompt`，source `{kind:'user'}`，合法，见 §C3 反证）。

会话用的模型是 `maas-glm-5.1-zhipu`（GLM via maas 适配器，见 seq 363 assistant/message source）——**疑似该 LLM 适配器或 DSH 工具执行链未为 tool-call 生成 callId**（模型侧不回 id 时 DSH 应兜底生成 UUID，此处写空串）。属 **DSH 侧 bug**（dsh-agent-loop / LLM 适配器 / 工具执行），非 sandore 插件所致。

## C3. 反证：sandore 不写 tool/call / tool/result

- sandore 全仓**从不构造 `tool/call` 或 `tool/result` 事件**（grep `'tool/result'`/`kind:'tool'`：生产代码只在 `subagents.ts` 的 `collectSessionMessages`/`finalAssistantOutput` **读取**这些事件，不写入）。
- sandore 写子代理会话 message 的唯一路径是 `deliverChildPrompt`（`subagent-delivery.ts`），经 queue 符号通道投递 **`user/message`**（`workflow-engine.ts` L352 `delivery(parent, childId, content, { kind: 'user' }, signal)`），source `{kind:'user'}`——对 `user/message` 而言合法（校验 L1177 只要求 `source.kind` 非空串），**不是 corrupt 的 `tool/result`**。
- 故 sandore 不可能产生 seq 365 这类 `tool/result` corrupt 事件。Bug #3 与 sandore 无关。

## C4. 性质判定 + 给 DSH 侧的建议（非 sandore 修复）

**性质**：DSH 侧 bug——`tool/call` 事件 `callId` 为空串，污染 `tool/result`，触发 rc.1 校验。AGENTS.md 禁止改 DSH 源码，故**本 Plan 不含 sandore 侧修复**（sandore 无责可修）。

**给 DSH 侧的定位/修复建议**（供上报或 DSH 升级时参考）：
1. `dsh-agent-loop` 工具执行：模型侧 tool-call 不回 `id` 时，DSH 应兜底生成 callId（UUID），不应写空串。查 `dsh-agent-loop` 写 `tool/call` 事件处（`data.callId` 赋值点）——疑似 `maas-glm` 适配器未回 id 且 DSH 未兜底。
2. 复现对照：用非 GLM 模型（如 DeepSeek）跑同一工作流，查其 `tool/call.callId` 是否非空——若非空则坐实是 GLM/maas 适配器特有；若仍空则 DSH 工具执行链通用 bug。
3. 已 corrupt 的会话（c6b17916 等）：rc.1 校验对历史数据不宽容（单条空 callId 即整会话 corrupt）。DSH 侧可考虑校验降级（空 callId 时跳过/告警而非判 corrupt），或迁移修复历史事件。

> 与 Bug #2 不同源：Bug #2 是 sandore `sessionEventList` 裸调（rc.1 适配）；Bug #3 是 DSH 工具执行写空 callId（与 sandore 无关）。两者恰好都暴露在 sandore 子代理会话上，但 Bug #3 责任在 DSH。

### D2.1 `loop-manager.getActualStepId` 返回纯 UUID（保留去重语义）

`packages/microflow/loop-manager.ts`：把 `stepIdSuffixMap` 存的「4 位 hex 后缀」改为「整 UUID」，`getActualStepId` 直接返回该 UUID（同迭代同 stepId 复用同 UUID —— 去重语义不变），`stripIdSuffix` 反查 UUID → 原始 stepId：

```ts
// 当前（broken）：
getActualStepId(originalStepId: string): string {
  const existing = this.stepIdSuffixMap.get(originalStepId);
  if (existing !== undefined) return `${originalStepId}-${existing}`;
  const suffix = LoopManager.loopIdSuffix();
  this.stepIdSuffixMap.set(originalStepId, suffix);
  return `${originalStepId}-${suffix}`;
}
stripIdSuffix(id: string): string {
  for (const [original, suffix] of this.stepIdSuffixMap) {
    if (id === `${original}-${suffix}`) return original;
  }
  return id;
}

// 改为（纯 UUID，去重靠 map 复用）：
getActualStepId(originalStepId: string): string {
  const existing = this.stepIdSuffixMap.get(originalStepId);
  if (existing !== undefined) return existing;          // 同迭代复用同 UUID
  const id = globalThis.crypto.randomUUID();
  this.stepIdSuffixMap.set(originalStepId, id);
  return id;
}
stripIdSuffix(id: string): string {
  for (const [original, actualId] of this.stepIdSuffixMap) {
    if (id === actualId) return original;                // UUID → 原始 stepId
  }
  return id;
}
```
